2.2사용자 흐름

  • 로그인
    회원가입 / 로그인 → Google → 닉네임(비우면 자동 생성) → 내 정보 입력 → 가입 완료
  • 조회
    메인 → 검색 · 탭 · 순위 → 상세 → 관련 고민 · 생각 · 활동 → 상세. 로그인 없이 볼 수 있다.
  • 작성
    작성 버튼 → (비로그인이면 로그인) → 작성 팝업 → 등록 → 해당 상세
  • 꿀팁 나눔
    고민 상세 → 이 고민에 꿀팁 나눔 → 고민이 채워진 작성 팝업 → 등록 → 고민 상세
  • 스케줄
    활동 · 생각 · 스케줄 담기 → 활동 바구니 → 스케줄 등록 → 활동별 요일 → 등록 → 스케줄 상세
  • 수정 · 숨김
    내 계정 또는 상세 → 수정 → 작성 팝업 → 저장 / 공개 ↔ 숨김
  • 반응
    상세 → 좋아요 · 댓글 · 활동완료 (로그인 필요)
  • 탈퇴
    내 계정 → 내 정보 수정 → 맨 아래 탈퇴 → 확인

3) 댓글, 좋아요

  • 댓글은 활동 · 꿀방울 스케줄 상세 화면에서 작성한다. 활동 · 스케줄을 숨기면 그 댓글도 보이지 않는다.
  • 좋아요는 고민 · 생각꿀팁 · 스케줄 · 활동 · 댓글에 누를 수 있다.
  • 신고는 고민 · 생각꿀팁 · 스케줄 · 활동 · 댓글에 할 수 있다. 같은 글에 3명 이상 신고하면 관리자에게 메일을 보낸다.

6.비기능 설계

6.1보안

  • 통신
    모두 HTTPS. 세션 쿠키는 HttpOnly · Secure · SameSite=Lax.
  • CORS
    허용하는 출처는 https://honeysaltlove.com (개발 중에는 http://localhost:3000)이다. 세션 쿠키를 실어 보내야 해서 allowCredentials 를 켠다.
  • CSRF
    웹은 세션 쿠키로 인증하므로 CSRF 보호를 켠다. 토큰을 쿠키로 주고(CookieCsrfTokenRepository, 쿠키 도메인 .honeysaltlove.com) 화면이 X-XSRF-TOKEN 헤더로 다시 보낸다. 화면(honeysaltlove.com)과 API(api.honeysaltlove.com)의 주소가 달라서, 화면이 토큰 쿠키를 읽으려면 쿠키 도메인을 .honeysaltlove.com 으로 둬야 한다. 앱 API(/api/app/**)는 쿠키 대신 헤더로 인증하므로 CSRF 검증에서 뺀다.
  • 앱 키
    해시만 저장한다. 원래 값은 처음 만들 때 한 번만 보여 준다.
  • 작성
    고민 · 꿀팁 · 스케줄 · 댓글 · 좋아요 · 의견 모두 로그인 후. 보기는 로그인 없이. 모든 작성 테이블의 member_id 는 NOT NULL.
  • 삭제
    삭제하지 않고 숨긴다(status HIDDEN · hidden_reason 에 '본인 삭제' 처럼 누가 · 왜). 작성자 · 운영자만. 활동 · 스케줄은 댓글이 있어도 삭제할 수 있다 — 그 댓글은 같이 안 보인다.
  • 숨김
    등록 시 바로 공개. 저장 뒤 비동기로 AI 검사 → 문제 있으면 HIDDEN + hidden_at + hidden_reason "AI: 광고". 신고 · 관리자 화면에서 HIDDEN + hidden_reason "관리자: …".
  • 입력 검증
    요청 DTO 에 @Valid · 글자 수 제한 · 오류는 400.
  • 헬스 체크
    Actuator 의 /actuator/health 만 연다(배포 확인 · 서버 감시). 설정값이 보이는 다른 Actuator 주소는 닫는다.

6.3대용량 기준

  • 테이블 나누기
    고민(honey_worry) · 생각꿀팁(honey_thought_tip) · 스케줄(honey_schedule)을 따로 둔다. 화면에서 쓰는 입력 항목이 달라서다. 생각꿀팁만 worry_id FK 로 고민을 가리킨다.
  • 숫자
    좋아요 · 사용자 수 · 활동 수 · 도움돼요 수 · 태그 사용 횟수는 호출마다 수정하지 않는다 — 인기 글에 몰려도 로우 락(row lock)으로 기다리지 않게. 원본 테이블(honey_like · app_done_log · app_helped_log · ○○_tag)에 기록하고, @Scheduled 스케줄러가 원본을 다시 조회해 개수를 구하고 *_count 를 갱신한다 — 집계 기준 시점을 따로 저장하지 않아 누락되거나 중복 집계될 가능성이 없다. 다시 세기는 원본에 기록이 생겼을 때만 돈다 — 기록 저장이 끝난 뒤 서버 메모리의 '변경됨' 표시(숫자 종류마다 하나)를 켜고, 스케줄러가 실행될 때 '변경됨' 표시가 켜진 숫자 종류(좋아요 수 · 사용자 수 등)만 전체를 다시 집계한다 (집계 전에 표시를 끄고, 표시는 저장이 끝난 뒤 켠다) (바뀐 것이 없으면 DB 를 조회하지 않음 · 서버가 시작될 때 전체 값을 한 번 집계한다). 좋아요는 1분마다(1분 동안은 실제 좋아요 수와 다를 수 있다) · 사용자 수 · 활동 수 · 도움돼요 수는 1시간마다 활동별로(사용자 수는 앱 키가 중복되지 않도록 세고) · 태그 사용 횟수는 1시간마다 공개 글만(글을 숨기면 줄어야 해서). *_count 는 UPDATE 쿼리로 갱신한다 — 엔티티로 고치면 글의 수정일까지 바뀐다. 스케줄 사용자 수(send_count)는 앱이 수신 완료를 알릴 때(ack) 1 올린다.
  • 활동완료
    app_done_log 은 가장 빨리 커진다. 지금은 일반 테이블(커지면 월별 파티션) · '사용자 N명 · 활동 N회'는 honey_activity 의 use_count · done_count 를 읽는다.
  • 많이 찾는 상황
    honey_worry_tag 를 매번 GROUP BY 하지 않고 tag.use_count 값을 조회한다(글이 바뀌면 스케줄러가 1시간 안에 다시 집계한다).
  • 보내기
    cart 는 앱이 수신 완료를 알릴 때(ack) honey_schedule.send_count 를 1 올리고 그 행을 바로 삭제한다.

8.1주요 결정과 이유

결정이유
화면 Nuxt 3 · 서버 Spring Boot + JPA상세 주소를 쇼핑몰처럼 정리하고 검색에 걸리게(SSR) · 백엔드 포트폴리오는 JPA 중심
로그인은 Google 계정으로만 제공해외 사용자도 이용할 수 있음 · 비밀번호를 직접 저장 · 관리하지 않아 관리 부담이 적음
웹은 세션 쿠키같은 도메인 · 서버 하나 · 로그아웃과 만료가 간단
앱은 앱 키 + 비밀값앱에 로그인 화면이 없어도 됨 · 기록은 앱 키만, 주고받기 · 웹 바로 접속는 비밀값까지 · 서버는 해시만 저장
승인 없이 등록 시 바로 공개운영자 1명 · 사용자가 기다리지 않음 · 문제 글은 AI 검사와 관리자가 숨김
태그는 @ManyToMany + @JoinTable연결 테이블에 추가 컬럼이 없어 엔티티가 필요 없음
목록은 페이지 번호 (page · size)정렬 기준이 여러 가지라(최신 · 좋아요 · 답 기다림 · 도움돼요) 정렬마다 쿼리를 나누지 않고 Pageable 에 정렬만 바꿔 넣음 · 현재 데이터 규모에서는 페이지 번호 방식으로 충분함 · 성능이 느려지는 목록에 한해 키셋(마지막 id 이후) 방식으로 변경
집계 숫자는 호출마다 갱신하지 않고 스케줄러가 맞춘다인기 글에 좋아요가 몰려도 로우 락(row lock)으로 기다리지 않음 · 값이 바뀐 경우에만 다시 집계하고, 변경이 없으면 DB 를 조회하지 않음
활동 바구니는 로그인 후 cart 에 저장웹에서 항목을 담아 앱으로 보내기 위해
API 주소는 /api/web/v1 · /api/app/v1웹은 서버와 같이 배포되지만 앱은 예전 버전이 폰에 오래 남아 버전을 따로 지킨다 · 인증(세션 · 앱 키)도 주소로 나뉜다
